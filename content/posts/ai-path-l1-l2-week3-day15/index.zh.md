## 毕业考核：L2 达成清单

4 周练习到这里。在宣布你"毕业"之前，请对照以下清单诚实自评。每一项后面跟一句说明，帮你判断自己是否真的过关。

- [ ] **能注册 API 账号，用 Python 发第一条请求并拿到回复**（Day 0-3）：不只是复制粘贴代码跑通一次。换一家 provider、换一个模型名，你能独立完成同样的事。

- [ ] **理解 token 计费、temperature 控制随机性、上下文窗口限制**（Day 0-3）：知道输入输出分别计费，知道 temperature=0 时输出是确定的，知道上下文太长会导致早期内容被挤出。不是背下来，是能解释给别人听。

- [ ] **写过至少一个批量处理脚本**（Day 4-7）：读文件→调 API→写结果。能跑通，能处理真实数据，不只在测试数据上成功。

- [ ] **会用自主执行型 AI 描述任务**（Day 8）：目标一句话、约束列清楚、预期输出说具体。不是堆一堆需求，是一次一个任务。

- [ ] **会用 GCO 框架把模糊需求拆成清晰指令**（Day 10）：拿到一个"帮我分析一下"的需求，能拆解出目标、约束、输出格式。而且能指出原需求缺了哪几项。

- [ ] **能用三种验证方法检查 AI 输出质量**（Day 11）：GCO 对照查"做了没有"、不变量检查查"变没变"、逆向检查查"哪里可能错"。不是每种都用，是知道什么时候用哪种。

- [ ] **能按"能不能定下来"判断任务归属**（Day 12）：提示词还是脚本，写提示词是判断活，跑提示词是体力活。这个判据能用在真实任务上，不只是纸上谈兵。

- [ ] **能看懂并修改一份 Skill 文档的四块骨架**（Day 13-14）：身份、输入、输出要求、质量要求。知道四块各自回答什么问题，知道怎么改一处不影响其他部分。

- [ ] **有一个自己的可复用脚本或技能包**（全篇实践）：可以是绘本流水线，也可以是一个批量翻译脚本。能跑通、能复用、能在需要的时候拿出来改。

## L2 结语

L2 的核心不是学多少工具。是学会一件事：**让 AI 替你做事**。

API 让它批量干活，Agent 让它自己规划，Skill 让它可复用。工具很多，底层逻辑只有一条——把你能定下来的东西定死，把定不下来的交给判断。

到任何一层停下来都是能力。开车不是非得会造车。L1 够用，L2 够用，L3 是另一次跃迁，不是必须。

## L3 往哪走

L3 的主题是：**从用工具到 Harness 架构设计**。

L2 教会了你有哪些工具、怎么用。L3 要回答另一个问题：当你有多个工具、多个 Agent、多条流水线时，怎么让它们一起工作？怎么设计工作流，让系统自己发现问题、修补缺口、持续改进？

### 核心认知：Harness 比 Prompt 更重要

L2 花了大量篇幅讲怎么给 AI 写提示词。到了 L3，一个反直觉的结论会出现：**真正决定多 Agent 系统能不能稳定运行的，不是 Prompt 写得有多好，而是 Harness（外骨骼）设计得有多严。**

Prompt 是软的——它依赖 AI 的"自律"。长链路里，AI 会漂移、会幻觉、会忽略约束。Harness 是硬的——它是运行环境里强制执行的规则，不依赖 AI 的理解力。一个设计良好的 Harness，能让即使不太聪明的模型也能稳定工作；一个设计糟糕的 Harness，即使最强模型也会崩。

L3 会围绕两个核心展开：**Harness 设计**和**多 Agent 工作流四环节（计划 → 实施 → 验证 → 反思）**。

---

### L3 内容规划

**第一部分：Harness 基础**

- **上下文工程**：`AGENTS.md` / `CLAUDE.md` 怎么写——不只是放指令，而是建立项目级的 Context 契约。静态规范（固定的规则文档）+ 动态上下文（运行时注入的信息）的分离与组合。
- **硬性约束**：Linter、Pre-commit、CI/CD 自动化校验。AI 生成的代码如果过不了 Linter，无论 Prompt 多好都不合格。软验证（AI 自检）和硬验证（机械规则）必须结合。
- **熵增治理**：长会话里上下文会膨胀、信息会衰退。什么时候该清理、什么时候该 checkpoint、怎么防止 Agent 在冗长对话中迷失方向。

**第二部分：多 Agent 通信与状态管理**

- **协议层**：MCP（Model Context Protocol）是什么，为什么需要统一工具标准。Agent 之间怎么通过标准化接口通信，而不是靠约定俗成的 JSON 格式。
- **状态管理**：State Drift 是什么、怎么产生、怎么预防。Checkpoint-Resume 机制——中断后怎么恢复，而不是从头重来。
- **架构模式**：Supervisor（集中路由）vs 流水线（顺序执行）的取舍。什么时候用单 Agent + 工具扩展，什么时候拆成多 Agent 协作。

**第三部分：四环节工作流落地**

每个环节都对应 Harness 设计的一个侧重点：

- **计划**：静态 Context 设计。`AGENTS.md` 定义全局 State Schema，限制 Agent 乱改全局状态。GCO 框架在这里是入口，但需要项目级契约支撑。
- **实施**：Harness 约束下的标准化执行。MCP 统一定义工具接口，多 Agent 通过协议通信而非自由发挥。
- **验证**：软验证（AI 自检）+ 硬验证（Linter/测试/CI）。Day 11 的三种方法属于软验证，L3 补上硬验证层。
- **反思**：错误库、置信度标注、元认知监控。反思结果写入静态规则，形成可复用的知识资产，下次循环直接读取。

---

这四个部分不是线性的——它们相互嵌套。Harness 贯穿整个四环节，协议和状态管理在实施阶段最集中，但反思结果又会反过来修改 Harness 的规则。L3 会逐步展开这些概念，每一步都会用具体的项目案例来讲，不会停留在抽象讨论。

如果你现在对 L2 的内容还有不清楚的地方，先回头巩固。L3 不急。
